title: Tenancy and isolation
description: One shared schema with row-level security keeps every tenant's data separate.
---

## Shared schema, enforced by the database

All tenants share one database and one set of tables. Every tenant-owned table has a `tenant_id` column, and
PostgreSQL **row-level security (RLS)** is the enforcement boundary: a query running for one tenant cannot read
or write another tenant's rows, even if application code has a bug.

This was chosen over a database or schema per tenant because that approach does not scale to thousands of
tenants: connection pools, backups and migrations all multiply.

## How the tenant is decided

For each request the service resolves the tenant from **one authoritative credential**, in this order:

1. **Site key** (website visitors): resolves the tenant on the public path.
2. **JWT `tenant_id` claim** (staff): resolves the tenant on the dashboard path.
3. **`X-Tenant-ID` header**: a *routing hint only*, used on unauthenticated routes such as login to pick which
   tenant's users to check.

If a credential is present and the hint names a different tenant, the request is rejected with `403` rather than
silently preferring one. This closes the "tenant confusion" attack where a header is layered over a valid token.

<Callout type="info">
The tenant is never taken from an ID in the URL. Staff only ever address their own tenant's data.
</Callout>

## Suspending a tenant

A platform operator can suspend a tenant. Tenant status is checked on every request, so a suspension takes
effect on the tenant's next call, with no need to wait for tokens to expire. Reactivating restores access.
